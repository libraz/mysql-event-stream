# パフォーマンス

## 目標

| 指標 | 目標 |
| --- | --- |
| デコードのレイテンシ | 1 イベントあたり 5 ms 未満 |
| スループット | 毎秒 100,000 行イベント超 |
| メモリフットプリント | 50 MB 未満 |

以下の測定値は `core/benchmarks` 以下のベンチマークハーネスによるもので、Apple M5 Max（18 コア、うち 6 つが性能コア）上の Release ビルドで実行しました。表の全体、正確なコマンド、各数値を取ったときのホストの条件は `core/benchmarks/BASELINE.md` に記録してあります。

## デコードのスループット

シングルスレッドでの毎秒あたりの行イベント数を、行の形ごとに示します。

| 行の形 | 行イベント/秒 | 行イベントあたり µs |
| --- | ---: | ---: |
| NULL 許容の INT 1 つ | 6,744,321 | 0.15 |
| 7 カラム、日付時刻と DECIMAL | 3,101,396 | 0.32 |
| 7 カラム、整数と文字列 | 3,395,970 | 0.29 |
| 28 カラム混在、INSERT | 1,977,437 | 0.51 |
| 28 カラム混在、UPDATE | 977,672 | 1.02 |

測定した中で最も幅の広い形——28 カラムで各行の両方のイメージを持つもの——でも、毎秒 100,000 という目標より 1 桁上にあります。

日付時刻と DECIMAL のカラムは `std::snprintf` を通さず桁を直接書き出しており、これらを含む形では 2.2〜2.6 倍の差になります。フォーマッタはフィールドごとに `localeconv_l` とそのプロセス全体のロックを通して小数点を解決するため、シングルスレッドのデコードでも費用がかかり、スレッドをまたぐとその費用がはるかに大きくなります。

## スレッドスケーリング

独立した `CdcEngine` インスタンスはアロケータもロケール状態もロックも共有しないので、どのスレッド数でも合計スループットが伸びます。

| 行の形 | 1 スレッド | 2 | 4 | 8 |
| --- | ---: | ---: | ---: | ---: |
| 7 カラム、日付時刻 | 3,655,937 | 1.89× | 3.51× | 5.31× |
| 7 カラム、文字列 | 4,072,881 | 1.81× | 3.44× | 5.50× |
| 28 カラム、1 イベント 50 行 | 1,998,903 | 1.51× | 2.27× | 4.78× |

8 スレッドで 8 倍ではなく 4.8〜5.5 倍に留まるのは、ホストの性能コアが 6 つ、効率コアが 12 つだからです。行あたりのワーキングセットが最も大きい形が、目標から最も離れます。

## キューに入ったイベント 1 つあたりのメモリ

保留中のイベント 1 つが保持する量を、行の形ごとに示します。

| 行の形 | イベントあたりのバイト数 | 10,000 イベント |
| --- | ---: | ---: |
| NULL 許容の INT 1 つ | 241 | 2.4 MB |
| 7 カラム、日付時刻と DECIMAL | 657 | 6.6 MB |
| 28 カラム混在、INSERT | 2,418 | 24.2 MB |
| 28 カラム混在、UPDATE | 4,659 | 46.6 MB |
| 28 カラムと 8 KB の注釈、1 イベント 1 行 | 10,667 | 106.7 MB |
| 28 カラムと 8 KB の注釈、1 イベント 50 行 | 2,585 | 25.9 MB |

この幅は 3 つの効果で説明できます。

行のカラム格納が支配的で、償却が効きません。28 カラムの書き込みは、1 イベントあたりの行数がいくつであっても 2,420 バイトから 3 バイト以内に収まります。各行が自分のカラム配列を持つからです。`UPDATE` は両方のイメージを保持するので、その 2 倍を払います。

MariaDB の `ANNOTATE_ROWS` の SQL 文は、行ごとではなく `ROWS` イベントごとに課金されます。1 つの文を、それが注釈するすべての行が共有します。8 KB の文なら、1 イベント 50 行のときは 1 行あたり 164 バイト、イベントが 1 行しか持たず共有する相手がいなければ 8 KB です。

スキーマによってこの 40 倍の幅が出るので、キューはエントリ数だけでなくバイト数でも上限を設けています。既定の 10,000 エントリが効くのは 1 イベントがおよそ 5 KB 未満のあいだだけで、それを超えるとリーダーを先に止めるのは 48 MiB のバイト予算です。[バックプレッシャーと上限](backpressure.md)を参照してください。

## 時間の行き先

ホットパスは、行デコーダのカラムループ、エンジンのフィード時のバッファリング、そして C ABI 境界でのマーシャリングです。

ソケットの手前に置いた先読みバッファは、binlog のパケットサイズ（64 バイトの読み取り）では素の `recv` に対して 36 倍の効果があり、64 KiB の容量以上では 2〜5% の費用になります。これは同じ測定を繰り返したときのばらつきの範囲内です。

Python では、カラムのマーシャリングが 1 行あたりの費用のうち、7 カラムの行で 33%、28 カラムの `UPDATE` で 73% を占めます。C のバッファに固定長のウィンドウを重ねてスライスし、カラムのペイロードを複製しています。代わりにカラムごとに `ctypes.string_at` を 1 回呼ぶと、カラムが 2 つ以上あるどの形でも 1.37〜1.47 倍の費用になります。行のペイロードのサイズでは、libffi の呼び出しあたりの固定費が複製の費用を上回るからです。
