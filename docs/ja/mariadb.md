# MariaDB

MariaDB 10.11 以降は MySQL と並んで、同じ API でサポートしています。フレーバーは接続時に検出され、`flavor` / `client.flavor` が示すので、設定でフレーバーを指定することはありません。

違いは 4 つあり、いずれもクライアントの内側で処理します。

## GTID の形が違う

MariaDB の GTID は MySQL の `uuid:seq` ではなく、`0-1-4711` のような `domain-server-seq` です。`currentGtid` / `current_gtid` が公開するチェックポイントはこの形を使い、この形の `startGtid` はそのまま送られます。MySQL の単独トランザクション形式に施される範囲への拡張は適用しません。[チェックポイントと復旧](checkpoints.md)を参照してください。

トランザクションごとの GTID イベント（型 162）は、クライアントが `@mariadb_slave_capability = 4` を通知して初めて現れます。クライアントはダンプを要求する前にこれを通知します。通知がなければ、サーバーはこのイベントを含まない旧来のレプリケーション形式にフォールバックします。

## ANNOTATE_ROWS が SQL 文を運ぶ

MariaDB は、ある行変更の集合を生んだ SQL 文を、その手前に置く `ANNOTATE_ROWS` イベントとして記録できます。この文はイベントの `sourceSql` / `source_sql` に届きます。

成立には 2 つの条件があります。サーバーがそのイベントを記録していること（`binlog_annotate_row_events=ON`）と、ダンプ要求がそれを求めていることです。後者はこのクライアントが送るすべての要求が満たします。どちらかが欠けると `sourceSql` は空文字列になります。

1 つの `ANNOTATE_ROWS` が対応するのは 1 つの行イベントではなく SQL 文の全体です。行データがサーバーのイベントあたりのサイズ上限を超える文は、連続する複数の `ROWS` イベントに分割され、その単一の注釈を共有します。そのため同じ文のテキストが、その文が生んだすべての行に現れます。

SQL 文は一度だけ保持され、それが注釈するすべてのイベントで共有されます。8 KB の文を行ごとに持たせると、キューに入ったイベントの費用をそれだけで占めてしまいます——[パフォーマンス](performance.md)を参照してください。

## 設定チェックが違う

MariaDB に `gtid_mode` 変数はなく、GTID の記録は `log_bin` に従うので、このチェックは飛ばします。代わりに `log_bin_compress` が `ON` であってはなりません。MySQL の `binlog_transaction_compression` を `ON` にできないのと同じ理由です。[サーバー設定](server-setup.md)に両方の設定があります。

## チェックサムの交渉は古い名前を使う

MariaDB は、MySQL 8.4 が読む `@source_binlog_checksum` ではなく `@master_binlog_checksum` を読みます。クライアントは検出したフレーバーに合う方を送ります。

## 変わらないもの

パーサーより上はすべて同じです。`ChangeEvent` のフィールドは同じで、カラム値の対応も同じ、フィルタの挙動も同一、エラーコードも同じ数値です。どちらの E2E スイートも、MySQL コンテナに対するのと同じテストを MariaDB コンテナに対して実行します。
